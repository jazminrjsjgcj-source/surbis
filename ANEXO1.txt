4. LAS CINCO REGLAS QUE MÁS TIEMPO AHORRAN

Este documento es largo y describe muchas cosas. Si solo se retienen cinco reglas, que sean estas: en el proyecto anterior, PUNTA, fueron responsables de la mayor parte del tiempo perdido y del trabajo que hubo que rehacer.

20. TAMAÑO DEL CÓDIGO

Ningún archivo principal de aplicación debería superar 500 líneas.

Esto aplica especialmente a:

500 líneas es un límite máximo, no un objetivo.

Si un archivo se acerca a ese tamaño, debes revisar si tiene demasiadas responsabilidades.

CÓMO SE MIDE

Un límite aplicado sobre una medida equivocada hace refactorizar lo que no toca y deja intacto lo que sí. En PUNTA se midió mal de tres maneras distintas:

text
Contar "hasta el siguiente function" MIENTE.
  Un constructor con propiedades promovidas seguido de constantes parece de 189
  líneas y tiene once.

Contar desde la línea de la firma MIENTE si la firma ocupa varias líneas.
  Un método con cuatro parámetros declarados en cuatro líneas se midió como
  "2 líneas" y tenía 57.

Contar líneas totales MIENTE cuando el archivo es mayoritariamente comentario.
  Un modelo de 1.090 líneas tenía 472 de código real.

La medida correcta es: desde la firma hasta su llave de cierre, ignorando cadenas y comentarios. Y para juzgar el tamaño de un archivo, medir el código real.

Un archivo puede crecer en líneas y encoger en código cuando se documenta bien:

text
eso es progreso, no regresión

23. LO QUE SE FABRICA EN DOS SITIOS SE COMPARA CON UNA PRUEBA

Cada vez que el servidor y el navegador construyen la misma cosa, las dos versiones se separan. Siempre. Y cuando se separan no falla nada: el resultado se ve distinto según cómo se haya llegado a él.

Casos reales de PUNTA:

text
un elemento que la vista pintaba al cargar y el JavaScript fabricaba al añadirlo
un catálogo de textos duplicado en un archivo JS que no consultaba la base
dos funciones que traducían al mismo formato desde orígenes distintos
la misma lista de columnas escrita en cuatro consultas

La regla, en dos niveles:

text
PRIMERO: que no haya dos sitios.
Lo que va atado —las columnas y el formateador, el contenido y su nombre de
archivo, la cita y su clave— viaja junto en una sola pieza, y entonces no se
puede coger una sin la otra.

SI NO SE PUEDE EVITAR: una prueba compara los dos.
Aunque sea comparando texto del código fuente: lo que se olvida en estos casos
es escribir el atributo, y eso lo caza una comparación de texto.

41. LOS CONTRATOS CON EL NAVEGADOR SON CONTRATOS

Un JSON que consume un archivo JavaScript no es «la respuesta de una pantalla»: es un contrato con un consumidor que vive fuera del proyecto y que no avisa cuando se rompe.

En JavaScript, leer una clave que no existe da undefined, se pinta vacío y no hay error en ninguna parte.

text
Vive en su propia clase, con nombre, no dentro de un controlador.
Tiene una prueba que fija sus claves, una por una.
Carga sus relaciones DENTRO de esa clase: quien pide el dato no tiene por qué
saber qué consultas hace.
Añadir una clave es seguro. Quitarla o renombrarla es un cambio con consumidores.

Vale igual para cualquier estructura que cruce la frontera del proyecto: respuestas de API, formatos de exportación, ficheros que otro sistema lee.

70. LOS FIXTURES DE PRUEBA DEBEN USAR LA FORMA REAL DE LOS DATOS

En PUNTA ocurrió de las dos maneras posibles:

text
Un fixture inventó los nombres de las claves de un array. El servicio también los
leía mal. Dos errores que se cancelaban: la prueba pasaba y el sistema estaba
roto. Al arreglar el servicio, la prueba se puso roja y PARECÍA que el arreglo
había roto algo.

Un fixture creó un registro sin una columna NOT NULL. Trece pruebas reventaron a
la vez en el mismo insert. Este salió barato: falló de inmediato y en voz alta.

Reglas:

text
Antes de escribir un fixture, leer el contrato real: la migración, el modelo, la
fábrica o el servicio que produce esos datos.

Si el fixture describe el envío de un formulario, escribirlo entero y a mano, no
generarlo: quien lea la prueba dentro de un año tiene delante la forma real del
envío, que si no habría que reconstruir leyendo las reglas de validación.

Si una prueba se puede escribir sin base de datos, escribirla sin base de datos.
Una función pura se prueba en milisegundos.
71. LA PRUEBA DEBE MONTAR EL ESTADO REAL DE AUTORIZACIÓN

En PUNTA se cometió TRES veces el mismo error, la segunda después de haberlo diagnosticado y corregido la primera:

text
crear el usuario con una etiqueta de rol NO le da permisos

El síntoma engaña porque no menciona permisos: la prueba falla con un 403 donde esperaba un 200, y parece un problema de la ruta.

text
Los permisos salen del control de acceso, no de una columna.

Son tres piezas y la tercera es la traicionera:
   1. sembrar los roles y permisos
   2. enganchar el rol al usuario
   3. OLVIDAR LA CACHÉ DE PERMISOS

La tercera importa porque esa caché va por id de usuario y entre pruebas los id
se repiten: sin limpiarla, una prueba hereda los permisos de la anterior y el
fallo aparece o no según el ORDEN de ejecución.

Esto se resuelve con un rasgo compartido, y el rasgo lleva escrito el porqué. No para ahorrar líneas: para que el error no se repita una cuarta vez.

Y se prueba con el rol que de verdad hace el trabajo, no con el administrador:

text
con un rol que tiene comodín de permisos la prueba pasaría siempre, incluso si
alguien retirara el permiso al rol real por error

73. TRINQUETES: FIJAR UN NÚMERO Y NO DEJARLO SUBIR

Hay deuda que no se puede eliminar de golpe: doscientos estilos inline, cien textos que no se muestran, cuarenta literales sin constante. Prohibirla de golpe no es realista. Dejarla sin vigilar garantiza que crezca.

La solución que funcionó en PUNTA:

text
una prueba que cuenta cuántos hay
una constante con el número conocido
si sube, la prueba falla
si baja, se actualiza el número: eso es progreso

Tres lecciones, las tres aprendidas rompiéndolos:

text
1. Un trinquete con la ruta de archivo escrita a mano SE APAGA EN SILENCIO el día
   que alguien mueve el código: deja de encontrar nada y deja de comprobar nada.
   Debe recorrer carpetas y FALLAR si no encuentra lo que vigila.

2. No basta con contar: hay que fijar DÓNDE están. Una mudanza puede dejar el
   total intacto y la lista mintiendo.

3. Sumar el total de varios archivos es peor que no comprobar: un cambio que
   añade en uno y quita en otro pasa desapercibido.

Y una regla de conducta:

text
NUNCA subir el número de un trinquete para que quepa un cambio propio.

Si el cambio lo hace subir, o el cambio está mal, o el trinquete ya no describe
lo que se quería vigilar — y entonces se rehace, no se afloja.

El histórico del número se conserva en el propio archivo de la prueba, con el motivo de cada bajada. Es lo que permite distinguir progreso de maquillaje.

75. ANTES DE REFACTORIZAR: INVENTARIO DE PRUEBAS

La sección anterior dice que hay que leer las pruebas. Esto es más estricto, y es la práctica que más tiempo ahorró:

text
1. Listar qué ramas tiene el código que se va a tocar.
2. Buscar qué prueba cubre cada una.
3. Escribir las que falten Y ENTREGARLAS SOLAS, sin tocar el código.
4. Verlas pasar contra el código VIEJO.
5. Solo entonces, refactorizar.

El paso 3 parece un rodeo y no lo es:

text
una prueba escrita DESPUÉS describe el código nuevo
una prueba escrita ANTES describe el comportamiento que hay que conservar

Son cosas distintas, y solo la segunda sirve de red.

El paso 4 tampoco es opcional: una prueba nueva que nunca se ha visto pasar puede estar mal escrita, y entonces no es una red, es un adorno.

Cuando el inventario sale bien —el código ya está cubierto— se refactoriza directamente y se dice por qué se puede. El inventario se hace siempre; escribir pruebas, solo si faltan.

84. MECÁNICA DE ENTREGA

Nada de esto es programación, y es lo que más veces obligó a rehacer trabajo en PUNTA.

text
EL ERROR MÁS CARO, REPETIDO CINCO VECES:

construir una entrega partiendo del repositorio original en vez de la última
versión entregada de ese mismo archivo.

Cada vez revirtió trabajo ya confirmado. Una de ellas tumbó la aplicación entera: al perderse una ruta que el layout carga en TODAS las pantallas, cualquier página devolvía error 500 y fallaban más de cien pruebas.

Reglas:

text
Antes de empaquetar, contrastar cada archivo contra la última versión ENTREGADA
de ese archivo, no contra el punto de partida. Con el proyecto en git, pedir el
archivo actual antes de reconstruirlo.

La entrega es ACUMULATIVA: cada paquete se construye sobre el anterior.

Comprobar que el paquete se extrae bien en el sistema operativo de destino. Un
archivo repetido dentro de un paquete puede guardarse como enlace duro y
extraerse con cero bytes en otro sistema.

Junto al paquete van los comandos que hay que ejecutar después: limpiar la caché
de vistas si se tocó una plantilla, la de configuración si se tocó la
configuración, la de rutas si se tocaron rutas.

Una caché no limpiada parece un cambio que no funcionó, y se pierde media hora
buscando en el sitio equivocado.
85. VERIFICACIÓN MECÁNICA ANTES DE ENTREGAR

Se hace siempre, aunque el cambio sea de dos líneas.

text
Llaves, corchetes y paréntesis balanceados, IGNORANDO cadenas y comentarios.

En plantillas, profundidad de anidamiento línea a línea. Contar aperturas y
cierres en total NO basta: dos errores contrarios se compensan.

Limpiar los comentarios de plantilla ANTES de contar etiquetas: una etiqueta
citada dentro de un comentario cuenta como apertura y produce falsas alarmas.

Comprobar que los comentarios de plantilla abren y cierran bien. Formatear texto
que contiene llaves puede convertirlas y hacer que el comentario se imprima en la
página.

Comparar el CÓDIGO REAL —sin comentarios— antes y después. Lo único que debe
aparecer o desaparecer son los cambios esperados.

Retirar imports, dependencias y variables que quedaron sin uso; comprobar que los
que se creen en uso lo están.

La comparación del código sin comentarios es la más valiosa de la lista:

text
es la que descubre lo que uno movió sin darse cuenta

DISCIPLINA DEL ANÁLISIS ESTÁTICO

Una herramienta de análisis sirve mientras alguien lea lo que dice.

text
Elegir un nivel que produzca avisos legibles, no miles que nadie lee.
Subir de nivel cuando el actual esté limpio, nunca de golpe.

Cada aviso silenciado lleva escrito AL LADO por qué se silencia y qué se
comprobó. Un archivo de exclusiones sin explicaciones es una lista de mentiras
futuras.

Configurar la herramienta para que crea al CÓDIGO y no a los comentarios. Con
eso, una anotación no arregla un aviso: lo arregla un cast, una rama por defecto
o una comprobación. Que es lo correcto.

Y una trampa concreta que costó una entrega entera:

text
Las plantillas de tipos de las colecciones NO son covariantes. Una colección de
elementos con forma exacta no cuenta como "colección de arreglos de cualquier
cosa", aunque cada uno de sus elementos encaje en esa descripción.

Cuando la herramienta rechaza una anotación correcta, la salida NO es engordar la
anotación hasta que calle: es quitar la promesa que no se puede verificar y

LA CATEGORÍA DE ERROR QUE MÁS CARO SALIÓ

La lista de arriba es de problemas de forma del código. El que más tiempo costó no está en ella porque no tiene forma:

text
un mecanismo plausible que no hace nada

No da error. No aparece en ningún log. La pantalla carga, el botón responde, el registro se guarda. Lo único que pasa es que el resultado no es el que nadie esperaba, y se descubre meses después.

Ejemplos reales, todos distintos y todos el mismo error de fondo:

text
un formulario pedía quince campos que ningún código leía
un botón guardaba el resultado de un cuestionario en un campo que se descartaba
265 textos de ayuda escritos, y solo 66 llegaban a mostrarse
una inyección de contexto quedó inalcanzable por un return mal puesto
un servicio leía claves de un arreglo que no existían y recibía datos vacíos
un panel mostraba "Sin folio" en todas sus filas por no pedir esa columna
una bitácora guardaba el hash de un archivo distinto del que entregaba
un camino entero del asistente de alta llevaba meses sin poder ejecutarse

Reglas que se derivan:

text
Todo campo que un formulario pide debe tener un consumidor demostrable. Si no se
puede señalar la línea que lo guarda, el campo se retira o se arregla.

Todo texto, catálogo o configuración escrito para mostrarse debe llegar a
mostrarse. Contarlos es barato y se automatiza.

Toda rama de código debe ser alcanzable. Si ninguna petición puede entrar en
ella, se retira: el código muerto no es neutro, se lee, se mantiene y se copia.

Un valor por defecto puede estar tapando que el dato nunca llegó. Cuando se
escribe uno, hay que saber qué caso real cubre.

La solución tampoco aquí es añadir capas. Es que cada cosa que se pide tenga un destino comprobable.
